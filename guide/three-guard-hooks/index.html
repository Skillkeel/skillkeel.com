The two hooks whose authors wrote test cases catch mostly their own

I keep a public set of 105 tool calls for testing Claude Code guard hooks, called tamper-cases. 83 of them are things a guard should stop and 22 are ordinary calls it should let through. A runner hands each call to a hook the way Claude Code would, as a PreToolUse event, and writes down whether the hook refused it. No model is involved, so a hook should give the same row every time.

On 22 September I ran my own hook through it, and dcg, a guard by another author. The third, lumis scope_guard, was run by its author, who sent the results as a pull request on 20 September. Its newer commit 9bbd581 refuses the same calls and asks for confirmation on eight more: six attacks, two of them git-settings cases, and two ordinary calls. That row is in the repo.

53 of the 105 cases are mine. They come from the tests of guard-bash, the hook I ship in Skillkeel's free Starter plugin, and Skillkeel also sells a paid kit. The other 52 come from lumis-skills, whose author built scope_guard and posted about trying 40 ways to make a coding agent rewrite it. 12 of those 52, cases 41 to 52, carry my handle in the author's file: they came out of the thread under that post, where I suggested them. The lumis cases attack a guard script and its files in lumis's own layout. Mine are destructive commands and git settings that run a program.

The table

The last row is my own hook, and I wrote 53 of the cases, so read that row with both in mind. Refused means the hook blocked the call. False positives are ordinary calls, like rm -rf node_modules or git branch -d old, that it blocked anyway. n/a means the hook does not look at that kind of call: two of the three read only Bash commands, so the 10 Write and Edit cases do not apply to them. The guard-file column's 50 cases target lumis's files (scripts/scope_guard.py, .lumis/), so for dcg and guard-bash they test whether an agent can rewrite someone else's guard script, which neither of them was built to protect.

Every row pins its release or commit, how the hook was called and the date, and the raw result for each call is in the repo. Rows were measured 20 to 22 September. dcg has had no release since v0.14.4; more than 100 commits have landed on its main branch since the run, none of them in a release or measured here.

What the table shows

The two hooks whose authors wrote cases each do best on those cases. lumis's guard refused 48 of the 50 attempts on its own files, and for 43 of those 48 it was the only one of the three that refused them. My hook refused all 12 git-settings cases, and among these three it was the only one that refused any of them; the repo's table has more hooks than this piece does. I wrote those cases, and then I wrote the rule that catches them. A hook passing its author's own tests says the author was consistent. It says much less about the attacks nobody on the list has written down yet.

So this is a coverage map. A low number in a column a hook never claimed is a different design, and the table says so in the cell.

Row by row

dcg is the largest project here, with about 6,000 GitHub stars (September 2026). With no config file it turns on three packs, and all four destructive calls it let through sit in packs that are opt-in: DROP DATABASE, redis-cli FLUSHALL, terraform destroy and chmod -R 777 /. That cell measures my configuration, and a re-run with those packs on is one issue away. It does not claim git-settings attacks at all. Its default protects credential files, and protection for its own config is in an opt-in pack that was off. Its six false positives include rm -rf build/ and git branch -d old, and they follow its stated policy of blocking an ordinary command before missing a dangerous one; its FAQ covers both forms.

lumis scope_guard is the reverse of mine: it covers the guard-file family almost completely, refused 11 of the 21 destructive calls and none of the git-settings ones; its README claims neither family.

My own hook misses 39 of the 40 guard-file cases it can see. guard-bash has no list of protected files, so a command that rewrites a guard script looks ordinary to it.

One call got past all three: python fix.py, where the script rewrites the guard. A hook that reads only the command cannot see what a script will do.

What would make this useful

A corpus written by two guard authors is a start. The cases that would change this table are the ones neither of us thought of. If you have a way past any of these hooks, including mine, open a pull request that adds it to cases.json with the call, where it came from and what it targets (the README section "Adding a hook or a case" has the fields). If you maintain one of these hooks and a row is wrong, or you want it re-run under a different configuration, open an issue and I will re-run it and keep the old row visible with the date.
